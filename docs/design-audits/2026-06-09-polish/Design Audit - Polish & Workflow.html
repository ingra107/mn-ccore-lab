PILLAR 1

Make it look good.

Visual consistency & polish. One width, one background layer, tokens that don't drift. The surface should look like one hand made it.

Three things make the Hub read "slightly off" everywhere at once: the centered column jumps width as you navigate, the light-mode page carries a tint behind its cards, and literal pixel values drift off the token scale. Each is a one-primitive fix.

1.1

One page-width rule

Tier-1 · Nick-flagged

The centered column has no single source of truth. Data pages use .content-container at 1440px; My Tasks Lanes caps at 1100px; Columns is colCount × 280 and scrolls horizontally; List is virtualized full-bleed. The column visibly resizes Today → Projects → My Tasks, and even between My Tasks' own three views. Nothing feels anchored.

Nick's real complaint isn't the number — it's that the focus moves when you switch tabs, while some pages waste a huge empty middle. So the rule isn't "two max-widths." It's one anchored column:

The fix — anchor the primary column; let rails extend outward. One centered content band on every page. Inside it, the primary column keeps the same left edge and the same measure everywhere. A right-hand helper rail (like Today's) lives in the space beside it — it never pushes or recenters the main column. Pages without a rail simply leave that space empty; the column you're reading stays exactly where it was. Switching tabs never shifts your focus, and a table never stretches across 1440px of empty middle.

Three tokens: --content-band (centered, identical on every page), --col-main (the anchored primary column — tables, lists, detail) and --col-rail (the optional right rail). The gold guide line is the invariant: the main column's left edge is the same pixel on Projects, My Tasks and Today. All three My Tasks views and every data page use --col-main; Columns still scrolls inside it. Dashboards (pure card grids) may fill the full band — the one documented exception. Zero per-page maxWidth literals.

PILLAR 2

Every click does something real.

Efficiency & no dead ends. One click should surface the whole control. Nothing should "come soon." No native alert should ever fire.

The single biggest "fall in love" lever: collapse the click-chains. The date picker is the archetype — but it names a whole class. And no control should promise a thing it can't do.

2.2

No dead controls. No native alerts.

P1

Every button does a real thing or it's removed. A PI in back-to-back meetings should never hit a control that shrugs. And the ethos is optimistic UI + undo toast — never a spinner or a browser alert() for an action.

  • MeetingNotesMeetingNotesPage.tsx:258, 341
    "Process Meeting" modal ships two dead controls: an Upload Audio tab that's a disabled "coming soon" drop zone, and Process Transcript, which only fires a "coming soon — AI not yet wired" toast.
    Until AI is wired: hide the audio tab entirely; make "Process" save the pasted transcript as a real note (the honest, useful action). No promise the app can't keep.
  • ProjectDetailProjectDetail.tsx:298–329
    Delete / duplicate failure paths fire native window.alert() dialogs (also MyTasks/index:185, SmartCompose:241, MorningThoughtCompose:84/100).
    Replace with the optimistic mutation + an undo/error toast already in the system. The jarring OS dialog is the opposite of "feels designed."
  • Settings · AISettingsPage.tsx:197
    The AI tab is a self-described "placeholder inputs" panel — really just a link to the Team Directory.
    Either fill it with the real settings it implies, or remove the tab and surface the Directory link where it belongs. An empty tab erodes trust in the rest.
  • Milestones / DeadlinesMenteeMilestonesPage:697 · DeadlinesPage:599

    Make the status control work on touch (it's the same field-editor primitive), or don't render it. A control that no-ops on tap is a dead end a phone user can't escape.

3.2

Trust: an honest clock, one staleness truth

Tier-1 · “current & correct”

You said the data being current and correct is one of the three things that would make you love it. Two things quietly break that trust. (a) The global status bar lies: StatusBar's “Last synced” resets to new Date() on any react-query cache success — so it reads “just now” even when the real PB→Hub sync is days stale. Meanwhile hoursSinceLastSync() reads the actual sync time and goes coral past 24h. The Hub shows you a green “fresh” signal that isn't true. (b) “Stale” means three different things: 10d on My Tasks chips, 14d in the dashboard + portal filter, 30d for manuscripts, and health-score < 50 for Projects — so “what's slipping” never gives one answer.

StatusBar.tsx:8–22 (fake lastSynced) vs today/constants.ts:121 (real) · stale: ColumnsView/ListView 10d · MyTasks.tsx 14d · manuscripts 30d · Projects.tsx:48 health<50
Status bar reads “just now” but PB synced 2 days ago
Last synced: just now
Real sync time, coral past 24h the truth
PB synced 2d ago · stale

Point the status bar at the real PB→Hub sync timestamp (the one Today already uses), coral past 24h per Rule 59 — a green clock must mean fresh. And pick one staleness definition (a single configurable threshold, the days-since-meaningful-movement already half-built) so every surface agrees on what's slipping. Trust is the cheapest, highest-leverage thing in this whole audit.

3.5

Mobile coherence

P2 · full sweep

You're desktop-first, but you want this done right for the 20-person team — so it's a full sweep this round. Audit task rows + controls at 360 / 390 / 768px (incl. the 768–1024px iPad-portrait nav split-brain) so nothing clips, overlaps or silently disables on touch.
