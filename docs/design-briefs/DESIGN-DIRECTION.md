# Design Direction — DD-1 through DD-7

**Date:** 2026-04-23 (round 5 close-out)
**For:** Nick / implementation agent triage. One paragraph per item + pillar + effort + skip-it.
**Companion:** `docs/specs/dd-3-status-line-pilot.md` (detailed layout spec — my Option C feedback below).

---

## DD-1 — Split every operational page into "Now" and "Data" views

**Proposes.** Every list surface (MyTasks, Projects, Manuscripts, Deadlines, Meetings, Decisions, Ideas, Grants, Activity) grows a view toggle in the page header — a single pill, `Now | Data`, URL-persisted as `?view=now|data`. **Now** is a 3-column status-report layout (Overdue / Today / Focus Next on MyTasks; At Risk / In Flight / Shipped on Projects; etc.) rendered at low density with a clear visual summary. **Data** is Airtable-dense — 32px row height, dense filter bar, keyboard-first (`j/k/x/Enter/n`), no hero strips or group-header visual breaks. Default is `data` on any surface with >20 rows, `now` otherwise. Every Now-view cell deep-links to Data with a focus parameter (`?view=data&focus={id}`) so the user moves between modes losslessly. **Pillar:** Airtable (commits to multi-view). Most density tickets in T-01–T-47 were symptoms of this mode-confusion; fixing them by splitting modes is the structural answer. **Effort:** 2+ sprints (pilot MyTasks + Projects in sprint 1, roll to the other 7 in sprint 2). **Skip it:** Degraded alternative exists — keep patching density surface-by-surface as tickets come in. The vision doesn't collapse, but you will keep re-litigating "how much hero-strip vs. how much table" on every page review, forever. Do this in round 7 at the latest.

## DD-2 — Saved cross-surface views (the product's most-valuable missing feature)

**Proposes.** A new abstraction: a **Saved View** is a filter `{project, window, owner, tags, entity-types[]}` that returns a merged stream across all 14 entity types. Ships as (a) a /views/* route that renders the stream, (b) a "Save as view…" action on any filtered search/activity/project-tab URL, (c) a user-curated pinned list in the sidebar below the fixed RESEARCH + LAB sections. Each saved view is a single URL, a single infinite feed, with entity-type badges on every row. This is Airtable Views + Linear Cycles + Notion Databases, scoped to MN-CCORE's 14-entity graph. It obsoletes Nick's TODAY.md file. **Pillar:** Airtable (Views) + MN-CCORE-specific (replaces TODAY.md). This is the single feature that changes what the Hub *is* — it turns a collection of tabs into a personal query tool. **Effort:** 2+ sprints (the query + feed exist in pieces — SearchPage's cross-type results + ActivityPage's unified stream — but wrapping them in a persistable filter model + sidebar-pin UI + URL serialization is real work). **Skip it:** Nick keeps TODAY.md forever. The Hub continues to receive ticket-after-ticket requests for "add filter X to page Y" which are all point-fixes for this pattern problem. Vision doesn't collapse but the Hub stays a tab-navigator instead of a query-tool. **This is the one I'd fight hardest for.**

## DD-3 — Operational status line on Dashboard (replace greeting)

**Proposes.** Replace "Good afternoon, Nick · Thursday, Apr 23" with a status line — same visual real-estate, every token operational: `● Live · 4 overdue · 3 due today · 2 regulatory expiring · last sync 11:42am`. Counts are clickable (deep-link to filtered views). The `● Live` dot is WebSocket connection state. "last sync" signals data freshness. Pilot on Dashboard only; if Nick doesn't miss the greeting after a week, codemod to Personal + Trajectory + ProjectDetail. **Pillar:** MN-CCORE-specific (PI-dashboard intent). Greetings are consumer-app idiom; Nick is a repeat-visitor power user — status beats warmth. **Effort:** 0.5 sprint (Dashboard-only pilot is 2 days; full codemod +3 days).

**On Option C (chip row) from the spec:** **Yes, ship Option C.** It's the right call for three reasons: (1) it matches the chip-strip pattern I already shipped on SearchPage + ActivityPage in round 5 (T-12, T-23), which means Nick's eye already reads "chip row = actionable filter" — we're reusing a learned pattern instead of inventing a new one. (2) Chips-as-actionable beats dot-separators-as-decoration — each chip becomes a clickable filter, not just a readout. (3) The chip row degrades gracefully to mobile (wrap instead of overflow), whereas Option A (single-line dot-separated) gets truncated awkwardly and Option B (two-line) eats vertical space on a page that already has density pressure. **One tweak for Option C:** the `● Live` WebSocket indicator should *not* be a chip — keep it as a bare leading dot + text so it reads as ambient status, not an action. Chips start at `4 overdue`. Also: chip counts of `0` should render as muted/disabled (not hidden) so the row's width stays stable across days — "0 overdue" at 40% opacity tells Nick he's clean, which is data worth showing.

**Skip it:** Keep the greeting. You lose the cheapest principle-test in the deck — 2 days of work that either validates or invalidates "operational, not editorial" as a product philosophy on the home surface. If you skip, at minimum rename the date line to surface ONE piece of data (e.g. `Thursday, Apr 23 · 4 overdue` inline). Don't do nothing.

## DD-4 — Presence with intent (viewing/editing/commenting states)

**Proposes.** The presence avatars shipped in T-13/T-14 show *who* is on a page. Add *what they're doing* — three states detected automatically from existing events: green dot (viewing, default), orange dot (editing, keystroke within last 10s), blue dot (commenting, compose bar focused + non-empty). No explicit user action. Plus a soft broadcast: when a user focuses a compose bar on a page where another user is present, the other user sees a subtle "Nick is typing…" indicator at the bottom of the page (Slack pattern, expires after 10s of no input). This is the T-51 typing-indicator work, generalized beyond the compose surface. **Pillar:** Slack (presence + typing) + MN-CCORE-specific (prevents two PIs from posting overlapping notes on the same meeting). Presence-without-intent is awareness without action; the 10-line delta from green-dot to orange-dot is what makes coordination *real*. **Effort:** 1 sprint (state detection is a debounce on events you already emit; broadcast reuses the presence channel). **Skip it:** Presence stays as a green-dot lurker-count. Users develop out-of-band habits ("ping me on Slack before you edit this meeting") that defeat the purpose of having the feature in-product. Vision doesn't collapse; the feature stays under-leveraged forever.

## DD-5 — Kill Welcome banner globally; replace with version-keyed "This week" ribbon

**Proposes.** Welcome banner ("Welcome to MN-CCORE Lab Hub — explore tasks, meetings, and research") still appears on Dashboard / Personal / Trajectory-Portal for Nick who has 576 completed tasks. Either dismissal doesn't persist, is scoped per-page, or re-raises on timeout. Replace with a weekly digest ribbon keyed to release version — shown Monday morning for one week after a meaningful ship: `This week: unified search (14 entity types), presence on project pages, mobile swipe-to-dismiss. Tell us what to try next →`. Auto-dismiss after 7 days or on click. Version in localStorage so a new release intentionally re-raises it. Solves onboarding (day-1 users still see a Welcome variant) and discoverability (Nick finds out Files tab shipped without Nate having to DM him). **Pillar:** MN-CCORE-specific (release-awareness for an internal tool where features ship faster than users notice). **Effort:** 0.5 sprint (component swap + version-keyed localStorage). **Skip it:** Welcome banner keeps nagging veterans; new features get discovered only via Slack announcements. Low-stakes but the cost of keeping the current banner is non-zero — it's the first thing Nick's eye skips every visit, and "things the user has trained themselves to ignore" is a UX debt that compounds.

## DD-6 — Display-number typography on hero stat cards

**Proposes.** PI Analytics, Lab Health card, Trajectory top row all render headline numbers (`100%`, `12.9d`, `$0`, `0 pubs`, `86 health`) at medium emphasis — same weight as the metadata labels below them. Pulse Kiosk already uses a 60px display-serif treatment for the same kind of number and it *works* — it's the product's best visual asset. Introduce a `<StatCard variant="display">` component: 60px display serif number, 11px all-caps gold label underneath, ~20% more card padding. Apply to the 4-6 hero stat rows, not to inline stats or table cells. Kiosk visual DNA is already brand-consistent — this is re-use, not invention. **Pillar:** MN-CCORE-specific (PI dashboards). The PI page is the biggest leverage point — it's what Nick screenshots to his chair. **Effort:** 0.5 sprint (one component + audit of 4-6 adoption sites). **Skip it:** Pages stay even-textured and undifferentiated — legible but with no visual anchor. Vision doesn't collapse; the Hub stays a quiet tool. If you want it to feel *confident*, this is the cheapest lever.

## DD-7 — Mobile parity sprint (6 surfaces × 6 fixes)

**Proposes.** Mobile is a second-class citizen but where Nick actually lives (between ICU rounds, on his phone). The 6 highest-traffic mobile surfaces (Dashboard, MyTasks, TaskDetail, ProjectDetail, Search, Cmd+K) each need the same 6 fixes: (1) Search promoted from "More" menu to a top-bar icon; (2) Compose becomes a bottom-sheet that rises above the keyboard (iOS/Android native pattern); (3) Swipe-left-archive / swipe-right-done on task rows (T-49 restored swipe-dismiss on the panel; extend that primitive to row-level); (4) Pull-to-refresh on every list; (5) Long-press on any entity → action sheet (delete / share / pin / copy link); (6) Haptics on destructive actions. **Pillar:** MN-CCORE-specific (ICU workflow reality). If Nick uses the Hub 10+ times/day and 3-4 of those are mobile, then 30-40% of usage happens on a surface that's under-designed relative to desktop. **Effort:** 2+ sprints (each item is 1-2 days × 6 surfaces, but there's shared infrastructure — bottom-sheet primitive, swipe-gesture hook generalized from T-49, haptic helper — which means sprint 1 is the infra and sprint 2 rolls it out). **Skip it:** Nick keeps the desktop tab open all day and mobile stays a "check-in only" surface, which self-fulfills the under-investment. This is the biggest user-facing-impact item in the deck. **Second-hardest to fight for, after DD-2.**

## Adoption order (my call, assuming Nick's capacity is the constraint)

1. **DD-3** (0.5 sprint) — pilot, tests the operational-not-editorial principle cheaply
2. **DD-5** (0.5 sprint) — pure win, banner lifecycle is broken
3. **DD-6** (0.5 sprint) — PI-dashboard brand moment, high visibility
4. **DD-4** (1 sprint) — completes the Slack pillar (presence → presence + intent)
5. **DD-7** (2+ sprints) — mobile parity; biggest user-facing impact
6. **DD-2** (2+ sprints) — saved views; biggest *product* impact
7. **DD-1** (2+ sprints) — Now/Data split; biggest restructure, do last

If Nick only picks two: **DD-3 + DD-7.** One teaches a principle; the other fixes where he actually works.
